Option 1 of 3
The Intelligence Layer
Build Andrew's "business brain" first — automate the weekly review cycle and make Dropbox AI-queryable.
01
Option 1 · Lower Risk · Highest Immediate ROI for Andrew
Build the Business Brain First
Before any ERP migration, before any field changes — automate the weekly intelligence cycle Andrew already runs manually. Connect Dropbox to AI querying. Template the multi-model decision workflow. Give Andrew his strategy advisor now, built on what's already working.
What Gets Built
1
Dropbox AI Index
Index Forma's Dropbox folder tree so Claude (or a configured AI layer) can search, retrieve, and summarize documents on demand. Andrew described this as a major asset — make it queryable.
2
Weekly Review Automation
Scheduled trigger pulls current P&L export, CRM summary from Sheets, and cohort data — packages into a structured prompt delivered to Claude and Gemini simultaneously. Andrew reviews outputs, not raw data.
3
Multi-Model Decision Templates
Pre-built prompt templates for recurring decision types (territory expansion, rep onboarding, cohort analysis). Andrew selects a template, fills inputs, and the system routes to 2–3 models and returns triangulated output.
4
ClickUp as Project Hub
Stand up ClickUp with three permission tiers (leadership / back-office / sales-read). Establishes project management and creates the foundation for future workflow integration.
Why This Path
⚡
Zero ERP dependency — everything in this option builds above the ERP layer. No risk from the pending decision.
🎯
Directly addresses Andrew's #1 stated pain — the weekly manual review cycle is the highest-frequency, highest-effort bottleneck.
📂
Unlocks existing asset — Dropbox is already "ridiculously organized." Indexing it costs low effort but has high strategic value.
🚪
Exit-ready intelligence — a documented, queryable business brain is a differentiator for future acquisition due diligence.
🧩
Modular by design — built as an API-connected layer. ERP swap later = swap one connector, not rebuild the brain.
Timeline Estimate
4–6 Weeks

Dropbox indexing (1–2 wks) → Weekly review automation (1–2 wks) → Multi-model templates (1 wk) → ClickUp setup (1 wk). Parallel tracks possible.

Tools Involved
Claude API · Dropbox · Make/n8n · ClickUp

Gemini stays as-is for Andrew's personal use. Grok remains manual (API gap — NOT VERIFIED). Google Sheets read-only integration for Sheets CRM data pull.

Field Team Impact
Zero

No changes to how sales reps operate. No new tools for the field. All changes affect Andrew and back-office only. This respects the rep compliance constraint explicitly.

Option 2 of 3
Inventory Process Automation
Tackle the highest operational risk area — consignment kit tracking — with a digital layer that sits above whatever ERP is chosen.
02
Option 2 · Highest Operational Impact · Moderate ERP Dependency
Digitize the Inventory Handoff
Replace the text/phone kit request system with a structured digital workflow — a request layer that creates a paper trail, sends confirmations, and prepares a clean data handoff to whichever ERP is selected. Pairs with velocity-based restock intelligence as a second phase.
⚠️
ERP Constraint Active. Phase 1 (request logging layer) can build now. Phase 2 (ERP write-back and restock triggers) must wait for ERP confirmation. Design Phase 2 now; build after decision.
What Gets Built
1
Kit Request Digital Layer (Phase 1 — Build Now)
Structured form (ClickUp, web form, or mobile) replaces the text/phone request. Rep submits: surgeon name, hospital, date, set list. System auto-confirms receipt, logs request with timestamp, notifies ops team. No ERP write — just a log.
2
Packing List Automation (Phase 1)
Once kit request is logged, system auto-generates a packing checklist for ops from the request data. Eliminates manual packing list creation — one of the top manual pain points in the inventory boards.
3
ERP Write-Back + Inventory Sync (Phase 2 — Post ERP Decision)
Kit dispatch confirmed in the request layer triggers a record in Odoo or Implantbase. Return logging closes the loop. Design the data model now; build the connector after ERP is selected — NOT VERIFIED until platform confirmed.
4
Velocity-Based Restock Intelligence (Phase 2)
AI layer reads dispatch history to flag SKUs approaching depletion. Surfaces reorder recommendations before manual check would catch them. Replaces the current Excel-based SKU reorder analysis.
Why This Path
🏥
Highest operational risk item — high-value orthopedic consignment assets moving with zero digital traceability is the most dangerous gap in the current state.
📋
Inventory board consensus — both inventory board variants flag kit request and packing list creation as top manual pain points. This directly targets both.
🔧
ERP-agnostic Phase 1 — the request log layer and packing automation don't care which ERP is selected. They capture data in a clean format ready for any destination.
📈
Sets up future serialization — the operating model notes "inventory not serialized now but maybe in future." This request layer is the foundation that makes serialization possible.
👥
Low-friction for reps — a simple structured form with auto-confirmation is likely more rep-friendly than the current text-and-hope system. But field change tolerance is low — must validate with reps before build.
Timeline Estimate
Phase 1: 3–5 Weeks
Phase 2: Post-ERP

Request form + packing automation (3–5 wks). ERP write-back design (parallel). Phase 2 build begins after ERP go/no-go gate.

Tools Involved
ClickUp · Make/n8n · Implantbase (Phase 2) · Odoo (Phase 2)

Phase 1 is ClickUp + automation platform only. Phase 2 tool list depends on ERP selection — NOT VERIFIED until Implantbase or Odoo confirmed.

Field Team Impact
Moderate

Reps replace a text with a form submission. Must be mobile-first and dead simple. High risk of non-adoption if friction is greater than current text method. Requires rep pilot before full rollout.

Implementation Standards
Constraints, Gates & Open Questions
Non-negotiables, human approval gates, and unresolved items that must be confirmed before build work proceeds.
Hard Constraints (Non-Negotiable)
🛑
No ERP-layer automation until ERP decision confirmed. Odoo vs. QB Online + Implantbase is unresolved. All ERP-touching builds are in design-only mode.
🛑
FDA Quality Management System is out of scope. No integrations, no disruptions, no assumptions. It is a compliance checkbox — not an AI integration target.
🛑
Sales rep change tolerance is extremely low. Any field-facing change requires a pilot before rollout. The prior CRM failure is a live precedent.
🛑
All AI outputs reviewed before action. "AI assists; humans decide" is the operating standard across all three options. No autonomous write-backs or decisions without human approval gate.
🛑
Architecture must be modular. No single-platform lock-in. Every connector should be swappable without rebuilding the intelligence layer above it.
Human Approval Gates
🔐
ERP Go/No-Go Gate — Client confirmation of Odoo vs. QB Online + Implantbase before any Phase 2 / Phase B builds begin. This is the critical sequencing gate for Options 2 and 3.
🔐
Current-State Sign-Off — Architecture before automation. Full current-state documentation and client review before any workflow builds begin. Andrew's workflow brain dump is the prerequisite.
🔐
Field Tool Pilot Gate — Any rep-facing tool (kit request form, activity logging) must complete a limited pilot and receive explicit client sign-off before org-wide rollout.
🔐
Inventory Process Sign-Off — Given the medical device context, any changes to inventory data or field mappings require explicit client approval. No assumptions on SKU, lot, or consignment data structures.
Open Questions — NOT VERIFIED
Implantbase API capabilities and data model
Not yet contracted. Phase 2 (Options 2 and 3) depends on what Implantbase exposes via API. Specifically: kit dispatch write, inventory level read, SKU/lot tracking fields, and consignment return logging. Must be verified before any Phase 2 design is finalized.
Odoo inventory module compatibility with Forma's orthopedic workflows
Odoo was deemed "a huge lift and very challenging to modify in the future" during discovery. If Odoo is selected, the extent to which it can handle consignment kit workflows without heavy customization must be confirmed before architecture design. The $150K NetSuite customization is the cautionary benchmark.
Grok (xAI) API integration path
Jessica confirmed no known platform integration with Grok exists. Andrew uses it heavily. If a multi-model routing system is built (Option 1 or 3), Grok's availability via API must be verified. If unavailable, the multi-model template system routes to Claude and Gemini only, with Grok remaining a manual addition.
Barcode / scanning compatibility for inventory
Flagged in the Open Questions tracker as unresolved. If inventory serialization is a future goal (noted in Operating Model as "maybe in future"), any request logging layer built in Phase 1 should be designed with barcode-compatible fields — but confirmed field structure requires client input first.
Exact outputs for AI-assisted strategy (from Open Questions Tracker)
The AI Implementation Board flags "exact outputs for AI-assisted strategy?" as an open item. Before multi-model templates are finalized (Option 1 / Option 3 Phase A), Andrew should define the specific deliverable format for each decision type — e.g., rep onboarding scenario: what does a "good output" look like?
QuickBooks Online Enterprise integration depth
Marc introduced QB Online Enterprise as a new option during discovery. Andrew was unaware of it. Its API exposure, inventory handling, and bi-directional sync capability with ClickUp are noted but NOT VERIFIED. If this path is selected, a formal capability audit is needed before any connector design.
